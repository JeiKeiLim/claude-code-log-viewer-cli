### Technical Wins

- **Story 10.1:** Re-scan eliminates initialization race condition window
- **Story 10.2:** Simple, effective user recovery with visual feedback
- **Story 10.3:** Platform-specific `GetBirthtime()` exports for reuse; `CreationTime` field added to Conversation struct
- **Cross-compilation verified:** Linux, Windows, FreeBSD all build successfully

### Root Cause Discovery

Epic 10's investigation revealed the true cause of BL-005:

> Claude Code modifies multiple OLD conversation files when starting a new session (likely syncing metadata). This causes the "latest modified" file to be an old conversation, not the current one.

**Evidence:**
- 11 files all modified within seconds of each other
- New conversation lost the mtime race
- Using birthtime correctly identified the new conversation

## Challenges & Growth Areas

### Story 10.3 Platform Complexity

Platform-specific birthtime required 4 separate files:
- `birthtime_darwin.go` - macOS syscall.Stat_t.Birthtimespec
- `birthtime_windows.go` - Win32FileAttributeData.CreationTime
- `birthtime_linux.go` - Returns zero (statx requires CGO)
- `birthtime_other.go` - Returns zero (fallback)

The pattern is clean but required careful attention to build tags.

## Key Lessons Learned

1. **Root cause > mitigation** - Story 10.1 and 10.2 were mitigations; Story 10.3 addressed the actual cause

2. **Birthtime is the right metric** - File creation time accurately identifies "newest" conversation, unlike mtime which can race

3. **Platform-specific code is manageable** - Build tags + graceful fallbacks make cross-platform support clean

4. **User recovery options matter** - Even with automatic fixes, manual refresh provides explicit control

5. **Code review catches timestamp bugs** - 2 HIGH issues were both related to using wrong timestamp fields

6. **Investigation before implementation** - 2026-01-29 investigation revealed the true cause, changing the approach
